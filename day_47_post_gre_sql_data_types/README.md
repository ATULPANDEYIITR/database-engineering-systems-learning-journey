# PostgreSQL Data Types: Numeric, Text, Boolean, UUID, JSON, and Arrays

## Scope

PostgreSQL provides distinct types for quantities, character data, logical states, identifiers, structured documents, and collections. Choosing an appropriate type determines which values can be stored, which operations are meaningful, how constraints behave, and which indexes can accelerate queries.

The accompanying implementations use an industrial equipment registry and telemetry records to demonstrate the differences. The Python and JavaScript programs focus on application-to-database boundaries. The C++ program models telemetry ingestion and validation. The Java program provides an enterprise-oriented equipment registry. The PostgreSQL script establishes the relational schema and executes type-specific queries.

## Numeric types

PostgreSQL provides integer types for whole numbers and decimal or floating-point types for fractional values.

| PostgreSQL type | Primary purpose | Important consideration |
|---|---|---|
| `SMALLINT` | Small whole numbers | Uses 2 bytes |
| `INTEGER` | General whole-number quantities | Uses 4 bytes |
| `BIGINT` | Large whole-number quantities | Uses 8 bytes |
| `NUMERIC(p, s)` | Exact decimal values | Precision and scale define permitted values |
| `REAL` | Approximate floating-point values | Uses 4 bytes |
| `DOUBLE PRECISION` | Approximate floating-point values | Uses 8 bytes |

The `NUMERIC(p, s)` declaration specifies maximum decimal precision and fractional scale. `NUMERIC(10,2)` supports eight integer digits and two fractional digits. A value such as `1499.95` is appropriate for exact decimal calculations, while a value with excessive fractional precision may be rounded or rejected depending on the input and constraints.

Python's `Decimal` and Java's `BigDecimal` provide decimal arithmetic suitable for financial and other precision-sensitive calculations. JavaScript's `Number` and C++ floating-point types use binary floating-point representations. Passing decimal values as strings across application boundaries helps preserve the original decimal representation until PostgreSQL processes the value.

The Python and Java implementations validate decimal precision before accepting records. The JavaScript example keeps exact numeric input as a string. The C++ implementation validates decimal text instead of converting it to a binary floating-point value.

PostgreSQL numeric constraints still matter even when an application validates the input. Multiple clients can write to the same database, and database constraints provide a shared integrity boundary.

## Text types

PostgreSQL's `TEXT`, `VARCHAR(n)`, and `CHAR(n)` types serve different requirements.

- `TEXT` stores variable-length character data without a declared maximum length.
- `VARCHAR(n)` stores variable-length character data subject to a character-count limit.
- `CHAR(n)` stores fixed-width character data and pads shorter values with spaces.

A serial number, manufacturer name, or communication protocol can be represented as text. A declared maximum length is useful when the domain has a real restriction, but an arbitrary length declaration does not replace semantic validation.

The application implementations validate non-empty strings and serial-number formats. The database schema makes serial numbers unique and prevents blank values. These are separate rules: a value can be valid text and still violate the serial-number requirements.

PostgreSQL text supports Unicode under a compatible database encoding. Application code should distinguish character-count limits from byte-count limits. The C++ example explicitly documents that its standard string-size check measures bytes rather than Unicode characters.

## Boolean values and SQL NULL

PostgreSQL `BOOLEAN` supports `TRUE`, `FALSE`, and `NULL`.

These states are not interchangeable. For equipment monitoring, `TRUE` can indicate that a device is active, `FALSE` can indicate that it is inactive, and `NULL` can indicate that its state is unknown.

SQL uses three-valued logic. A comparison involving `NULL` often produces `UNKNOWN`, not `TRUE` or `FALSE`. Queries should use `IS NULL`, `IS NOT NULL`, `IS TRUE`, and `IS FALSE` when the distinction matters.

The JavaScript and C++ implementations represent the nullable state explicitly. Java uses `Boolean`, while Python uses `None`. The SQL script uses a `CASE` expression to distinguish active, inactive, and unknown equipment states.

A nullable column is appropriate only when an unknown value has a legitimate business meaning. If the state must always be known, use `NOT NULL` and an explicit default where suitable.

## UUID identifiers

PostgreSQL's `UUID` type stores a 128-bit identifier. UUIDs are useful when records need identifiers that can be generated by separate application instances without relying on a single central sequence.

The SQL implementation uses `gen_random_uuid()` to generate identifiers. Python uses `uuid.uuid4()`, Java uses `UUID.randomUUID()`, and the JavaScript program uses Node.js's `randomUUID()`.

UUIDs can be used as primary keys and foreign keys. They reduce coordination requirements across distributed producers, although their larger storage size can be less compact than integer keys. UUIDs also do not provide authorization: possession of an identifier must not grant access to the corresponding record.

The Python and Java examples reject malformed identifiers before constructing domain objects. The database's UUID type performs the final type validation when values are inserted.

## JSON and JSONB

PostgreSQL offers two JSON storage types.

| Type | Storage behavior | Appropriate use |
|---|---|---|
| `JSON` | Preserves the input JSON text representation | Workloads that require retaining the original textual representation |
| `JSONB` | Stores a decomposed representation | Structured document queries and indexing |

`JSONB` supports operators for extracting fields, testing document containment, and accessing nested attributes. For example, `metadata ->> 'protocol'` returns a field as text, while `metadata -> 'calibration'` returns a JSONB value. The `@>` operator tests whether a document contains a specified JSON structure.

The SQL script stores calibration details and communication protocols in JSONB. It demonstrates field extraction, nested-path access, containment filtering, and a GIN index.

The Python and JavaScript implementations validate telemetry objects before serialization. They restrict permitted fields and validate pressure, quality state, and tags. The Java implementation wraps structured metadata in a domain type, while the C++ implementation explicitly notes that a simple boundary check is not a complete JSON parser.

JSONB is not a substitute for every relational column. Frequently queried attributes with stable meaning, such as equipment identifiers and pressure limits, are generally better represented as typed columns. Flexible metadata can remain in JSONB when its structure varies by device or producer.

JSON document validity alone does not guarantee business validity. A syntactically valid document can contain a negative pressure, an unsupported protocol, or an incorrect value type. Applications and database constraints should enforce the relevant domain rules.

## PostgreSQL arrays

PostgreSQL supports arrays of a declared element type, including `TEXT[]`, `INTEGER[]`, and arrays of other supported types. Arrays preserve element order and can contain `NULL` elements unless restrictions prevent them.

The equipment registry uses `TEXT[]` for labels such as `plant-a` and `critical`. The SQL script demonstrates array membership through `ANY` and creates a GIN index for array queries.

The application implementations validate array element types and reject duplicate labels. The SQL schema rejects null array elements, but it does not impose every application-level label rule. This distinction demonstrates why validation requirements must be considered across both layers.

Arrays are useful for compact, bounded collections that belong naturally to one record. A separate child table is generally more suitable when collection elements require their own identifiers, foreign keys, unique constraints, permissions, frequent independent updates, or detailed reporting.

Multidimensional arrays are also supported by PostgreSQL. Applications should use them only when their shape and semantics are well defined.

## JavaScript implementation

The JavaScript program represents a Node.js telemetry ingestion boundary.

It uses `randomUUID()` for identifiers, strict input checks for scalar values, regular expressions for UUID and decimal representations, and arrays for device labels. It deliberately transports exact decimal input as a string rather than converting it to `Number`.

The JSON validator rejects unexpected keys and invalid measurement values. It checks that pressure is finite and non-negative, verifies the quality state, and validates tag elements.

The optional PostgreSQL section uses the `pg` package. Parameters such as `$1::uuid`, `$2::numeric(10,2)`, `$5::jsonb`, and `$6::text[]` make the intended database types explicit. Parameter binding prevents input values from becoming executable SQL syntax.

The database driver determines how PostgreSQL values are represented in JavaScript. Numeric values are commonly returned as strings by `node-postgres`, which helps preserve decimal precision. Applications should inspect driver behavior rather than assume every database value maps directly to a JavaScript primitive.

## C++ case study

The C++ program models a telemetry gateway that validates incoming equipment readings before accepting them into a batch.

`NumericDecimal` validates decimal text against precision and scale constraints. `Uuid` validates UUID syntax. `TelemetryReading` groups the equipment identifier, serial number, pressure, nullable operational state, labels, and metadata.

The use of `std::optional<bool>` allows the gateway to represent a missing status separately from `false`. The vector of readings represents the accepted batch, while the rejection collection records validation failures.

The gateway illustrates a boundary between data ingestion and persistence. It does not implement the PostgreSQL network protocol or a complete JSON parser. In a production system, a real JSON parser and a PostgreSQL client library would handle document validation and parameterized database operations.

The decimal validator is intentionally conservative and educational. Applications that need exact PostgreSQL casting semantics should test inputs against the actual database, particularly for rounding, numeric special values, and boundary conditions.

## Java implementation

The Java program models an enterprise equipment registry with explicit domain types.

The `EquipmentId` record wraps a UUID. The `Pressure` record uses `BigDecimal` and enforces non-negative values, decimal scale, and precision. The `CalibrationState` enum defines explicit calibration states, avoiding unstructured status strings.

`JsonDocument` wraps structured metadata, and `Equipment` combines the typed fields into a validated domain record. The registry maintains a primary lookup by UUID and a second lookup by serial number.

The registry rejects duplicate identifiers and serial numbers. It can also identify equipment that requires calibration review. A nullable `Boolean` represents the unknown activity state, while `OffsetDateTime` stores a timezone-aware creation time.

This application-level model does not replace database constraints. Concurrent application instances could attempt to register the same serial number, so the database's unique constraint must remain authoritative.

The example uses Java 17 records and standard-library classes, with no third-party dependencies.

## PostgreSQL relational model

The SQL script creates an `industrial_registry` schema with three related tables.

| Table | Purpose | Important data types |
|---|---|---|
| `manufacturers` | Stores manufacturer identity and country information | `UUID`, `TEXT`, `VARCHAR(2)` |
| `equipment` | Stores equipment identity, pressure limits, status, labels, and metadata | `UUID`, `NUMERIC`, `BOOLEAN`, `TEXT[]`, `JSONB`, `TIMESTAMPTZ` |
| `telemetry_readings` | Stores time-stamped measurements and payload attributes | `UUID`, `TIMESTAMPTZ`, `NUMERIC`, `DOUBLE PRECISION`, `BOOLEAN`, `JSONB` |

The equipment table references manufacturers through a foreign key. Telemetry readings reference equipment and are deleted with their parent equipment records through `ON DELETE CASCADE`.

Constraints enforce non-empty serial numbers, unique identifiers, non-negative pressures, valid JSON object structure, and arrays without null elements. Indexes support manufacturer lookups, time-ordered telemetry retrieval, JSONB filtering, and label membership queries.

The sample inserts use `ON CONFLICT` to make the seed data repeatable. The script uses a transaction so that schema and sample-data operations can be committed together. The database remains responsible for checking column types, relationships, and constraints.

The `information_schema.columns` query shows actual database type metadata, including precision and scale. This is useful when validating application mappings or investigating unexpected database behavior.

## Type selection and design trade-offs

The most appropriate type depends on the meaning and operational requirements of the data.

- Use `NUMERIC` when exact decimal arithmetic or declared precision is important. Use floating-point types when approximate scientific calculations are acceptable.
- Use `TEXT` for variable-length character data. Add length checks when the domain imposes a real restriction.
- Use `BOOLEAN` when the value has two logical outcomes, and permit `NULL` only when an unknown state has meaning.
- Use `UUID` for identifiers that benefit from distributed generation or globally unique representation.
- Use `JSONB` for flexible structured attributes that need document queries or indexing.
- Use arrays for compact collections whose elements belong to one record and do not require independent relational management.

Type selection also affects indexing and query design. GIN indexes can help with appropriate JSONB containment and array membership queries, while B-tree indexes are suitable for ordinary equality, ordering, and relational lookup patterns. Indexes consume storage and add write overhead, so they should correspond to actual query requirements.

## Data integrity, security, and production behavior

Application validation improves error messages and rejects invalid input early. PostgreSQL constraints enforce shared rules regardless of which application performs the write. Both layers have distinct responsibilities.

Parameterized SQL is essential when inserting or querying values supplied by users or external systems. UUIDs should not be treated as access-control tokens, and flexible JSONB fields should not be accepted without meaningful validation.

For telemetry systems, timestamps should include timezone information, measurement units should be explicit, and decimal precision should match the physical or business domain. Unknown readings must remain distinguishable from zero measurements. JSONB and arrays should not obscure relationships that need foreign keys, independent updates, or reporting.

The final database design should be tested against actual PostgreSQL behavior. Application-language representations are useful abstractions, but database casts, null semantics, precision rules, and indexing behavior remain the authoritative properties of the stored data.
