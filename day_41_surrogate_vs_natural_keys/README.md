# Surrogate Keys vs Natural Keys: Identifier Design and Trade-offs

## Scope

Database keys determine how entities are identified, how relationships are represented, and how changes to business data propagate through an application. The choice between surrogate and natural keys affects relational integrity, data integration, index size, distributed processing, migration effort, and the long-term stability of an information system.

This project models a customer and order domain in which customers arrive from multiple source systems, business identifiers may be corrected, and repeated imports must not create duplicate records.

The implementations distinguish three separate concerns:

- **Entity identity:** which customer or order a database row represents.
- **Business identity:** which real-world entity a natural identifier refers to under a domain-specific uniqueness rule.
- **Source identity:** which record in an external system has already been imported.

These identities may refer to the same underlying entity, but they are not interchangeable.

## Natural keys and surrogate keys

A natural key is derived from a meaningful attribute or combination of attributes in the business domain. Examples include a jurisdiction and tax identifier, a country-specific registration number, or a source-system name paired with its record identifier.

A surrogate key is an identifier assigned specifically to distinguish a database entity. It has no required business meaning. Common examples include an identity-generated integer, a sequence-generated 64-bit integer, and a UUID.

A primary key is a database constraint identifying rows uniquely. It can be natural or surrogate. A candidate key is a minimal set of attributes capable of uniquely identifying a row. A table can have one primary key and multiple additional candidate keys enforced through unique constraints.

| Design property | Natural key | Surrogate key |
|---|---|---|
| Meaning | Represents a business identity | Represents internal entity identity |
| Generation | Supplied or governed by a domain | Generated by a database or identifier service |
| Stability | Depends on business rules and authoritative sources | Usually independent of business-attribute changes |
| Uniqueness | Must follow a documented domain rule | Must be enforced by the identifier mechanism and database |
| Relationships | May require multiple or lengthy columns | Usually uses one compact or fixed-width identifier |
| Integration | Can simplify matching when the identifier is authoritative | Requires mapping external identities to internal IDs |
| Privacy | May expose tax, account, or other business information | Can avoid exposing meaningful business attributes |
| Main risk | Corrections, reuse, normalization, or changes in meaning | Mapping errors, allocation problems, and unnecessary identity duplication |

A surrogate key does not establish business uniqueness. A customer table with generated IDs can still contain two records for the same legal entity unless the application and database enforce the relevant natural-key rules.

Conversely, a natural key is not automatically unsuitable as a primary key. A domain identifier that is authoritative, stable, compact, and reliably unique may be a reasonable primary key. The decision depends on the guarantees the domain can provide.

## Composite keys and candidate keys

Some entities cannot be uniquely identified by a single attribute. A tax registration might be unique within a jurisdiction but not globally. The pair `(country_code, tax_identifier)` can therefore represent a natural candidate key when the relevant legal rules support that interpretation.

A composite natural key has consequences for every dependent relationship. Foreign keys may need multiple columns, joins become wider, and corrections can affect many referencing records if the natural key is used as the primary key.

The Python, C++, Java, and SQL examples represent this jurisdiction-specific identity explicitly. They reject duplicate pairs rather than assuming that a company name is unique.

Composite-key correctness depends on normalization and domain semantics. Case sensitivity, whitespace, Unicode normalization, punctuation, jurisdiction, and changes in legal registration can all affect whether two representations identify the same entity. Normalization should follow authoritative business rules rather than arbitrary string transformations.

## Integer, UUID, and business-derived identifiers

### Integer identity

Database-generated integer identifiers are compact and generally efficient for joins and indexes. A 64-bit integer supports a large positive range and is often a practical default for centralized relational systems.

The Python, JavaScript, C++, and Java programs use local integer allocators to make identity assignment visible. Those allocators are demonstrations, not production distributed allocators. Separate application processes cannot safely use the same in-memory counter without coordination.

In PostgreSQL, `GENERATED ALWAYS AS IDENTITY` delegates generation to the database. A sequence can allocate distinct values across concurrent transactions, although gaps are expected after rollbacks, failed inserts, caching, or sequence advancement. IDs should not be interpreted as transaction counts, timestamps, or guaranteed gap-free business numbers.

### UUID identity

A UUID provides a fixed 128-bit identifier, often useful when independent services must create identifiers without contacting a central sequence. UUID v4 is random; UUID v7 includes a time-oriented component and can improve insertion locality in some database workloads.

The JavaScript implementation uses `crypto.randomUUID()` for order identity. The PostgreSQL script uses `gen_random_uuid()` as its order ID default. UUID generation reduces coordination requirements but does not replace primary-key constraints or application-level deduplication.

Random UUIDs generally require more index space than 64-bit integers and can produce less sequential index insertion. UUIDs should be evaluated against expected table size, index behavior, replication architecture, and operational requirements.

A UUID is not an authorization mechanism. Knowledge of an identifier must not grant access to a customer or order without independent authorization checks.

### Natural string identity

A business identifier can make integration and diagnostics easier because it is recognizable outside the database. It can also change, be reassigned, contain sensitive information, or require complicated collation and normalization rules.

Using a string as a primary key can increase the size of primary and secondary indexes. This matters when many tables reference the same key. The cost depends on the database, character encoding, collation, index implementation, and actual value lengths.

### Hash-derived identity

The Python and JavaScript examples derive deterministic SHA-256 digests from namespaced source identifiers. This provides a reproducible representation of the input, but a hash is not proof of business uniqueness.

A robust source mapping retains the original source-system and source-record values and enforces a unique constraint on the pair. A digest may be used as a lookup aid, but it should not be the sole basis for entity matching without an explicit collision-handling policy.

## Python implementation

The Python script combines an in-memory identity registry with a SQLite relational example.

`CustomerRegistry` assigns internal integer IDs and maintains an index from normalized email addresses to customer IDs. Registering a duplicate email fails, and changing an email preserves the customer ID. This demonstrates why a mutable business attribute should not necessarily serve as the permanent identity of an entity.

The natural-key example uses a country and tax identifier as a composite key. Replacing that key illustrates how natural-key corrections affect lookup structures.

The SQLite schema contains `customers` and `orders`. The customer ID is the primary key, email is unique, and each order references its customer through a foreign key. The external order reference is independently unique. Check constraints reject negative monetary amounts.

The script deliberately exercises invalid operations. Duplicate email insertion, nonexistent customer references, negative amounts, duplicate order references, and deletion of a referenced customer are rejected by the database.

SQLite foreign-key enforcement is enabled explicitly. Without that setting, foreign-key declarations alone may not enforce the intended behavior in every SQLite connection.

The demonstration uses an in-memory database, so it is self-contained and does not require a database server. The in-memory registry is useful for understanding identity relationships, but a production system needs durable storage and transactional coordination.

## JavaScript implementation

The JavaScript program models event-driven ingestion from an external ERP system. Each incoming order has an internal UUID and a source identity consisting of a source-system name and source-record ID.

The private fields in `OrderIngestionService` keep internal maps encapsulated. Events communicate successful customer registration, email changes, and order creation to listeners. The returned unsubscribe function allows listeners to be removed when their lifecycle ends.

Order ingestion is idempotent within the service instance. Reprocessing an identical source record returns the original order, while a retry with conflicting customer or amount data is rejected. This is important for systems in which queues, webhooks, or batch imports can deliver the same record more than once.

The implementation uses an asynchronous method to illustrate ingestion in a Node.js runtime. Its critical map-update sequence contains no `await`, so JavaScript callbacks in the same isolate cannot interleave inside that sequence. This is not a replacement for database transactions or concurrency controls across multiple processes.

The example also exposes a JavaScript-specific identifier problem. The `Number` type cannot represent every integer above \(2^{53}-1\) exactly. Large numeric business identifiers should be represented as strings or carefully handled with `BigInt`; JSON APIs commonly serialize identifier values as strings to avoid precision loss.

The in-memory maps do not provide durable idempotency. A production implementation must persist source identities under a unique database constraint so that retries remain safe after restarts and concurrent requests.

## C++ case study

The C++ program models a logistics customer master-data service that integrates records from acquired business systems.

`CustomerMasterData` maintains a customer registry, a natural-key index, an external-source index, and a shipment collection. The design separates customer identity from tax registration and source-record identity.

The customer registry uses a 64-bit surrogate ID. An ordered map indexes the composite country-and-tax key, while hash maps store entities by internal ID. A correction operation validates the replacement key before changing the index and customer record. The surrogate identity therefore remains stable while the business identifier changes.

Shipment ingestion checks that the customer exists, rejects negative declared values, and identifies repeated source records through the source-system/record pair. An identical retry returns the existing shipment ID. A conflicting retry is rejected instead of silently overwriting the earlier shipment.

The case study demonstrates useful complexity distinctions:

- Lookup by customer ID through the hash map has expected constant-time complexity.
- Lookup through the ordered natural-key index is logarithmic in the number of indexed customers.
- The demonstration's customer shipment query scans all shipments and is linear in the total shipment count. A production design would add an index keyed by customer ID.

The in-memory implementation also exposes its limitations. It has no durable transactions, no cross-process uniqueness enforcement, and no synchronization for concurrent access. The database constraints in the SQL implementation address the durable integrity portion of this problem.

## Java implementation

The Java program separates the customer identity service from the order service.

`NaturalCustomerKey` and `SourceKey` are records with constructor validation. Their equality and hashing behavior make them suitable as map keys. The natural key represents the country-and-tax-identifier pair, while the source key represents an external system's record.

`CustomerIdentityService` owns the mapping between surrogate customer IDs, natural keys, and external identities. `OrderService` manages UUID-based order identities, source-event deduplication, and a secondary index from customer IDs to order IDs.

The services use domain-specific exceptions to distinguish identity conflicts from invalid input. Natural-key corrections preserve the customer ID, so existing orders remain linked to the same customer.

The Java records are immutable value representations, but immutable records alone do not make the underlying maps transactional. The code is a single-process model and is not safe as a distributed identity service without persistent storage and concurrency control.

In an enterprise implementation, customer creation, natural-key registration, and external-source mapping should occur in one database transaction. Otherwise, an error between writes could leave an incomplete identity mapping. A database uniqueness constraint must remain authoritative even if application validation performs an earlier lookup.

## PostgreSQL relational model

The SQL script uses PostgreSQL and defines four tables:

| Table | Identity and responsibility |
|---|---|
| `customers` | Uses an identity-generated `BIGINT` primary key and a unique country/tax-identifier pair. |
| `customer_external_ids` | Maps source-system and source-record pairs to internal customer IDs. |
| `orders` | Uses a UUID primary key, references a customer through a foreign key, and enforces unique source order identity. |
| `customer_key_audit` | Records changes to customer natural identifiers, including old and new values. |

The customer and order tables use different key strategies because their requirements differ. The customer identity is a compact internal integer, while the order identity is a UUID. The source-system and source-record pair remains a separate uniqueness rule.

The database constraints enforce important invariants:

- Primary keys prevent duplicate internal identities.
- Unique constraints reject duplicate business identifiers and duplicate source records.
- Foreign keys prevent orders and external mappings from referencing nonexistent customers.
- Check constraints reject blank identifiers and negative monetary amounts.
- The customer natural-key audit trigger records changes to country and tax identifiers.

The indexes support customer order history and reverse lookup from external mappings to customers. The `orders(customer_id, created_at DESC)` index aligns with queries that retrieve a customer's most recent orders.

The SQL script also demonstrates staging-data collision checks using common table expressions. These checks reveal duplicate natural keys within an incoming batch and conflicts with existing master data before insertion.

The sample correction updates a natural identifier without changing the customer primary key. Existing order relationships remain valid, and the trigger writes an audit record.

The transaction groups the sample setup, import mappings, orders, and correction. PostgreSQL sequences and identity generators are not gap-free transactional numbering systems. The transaction provides atomicity for ordinary table changes, but allocated identifiers can still leave gaps after failures.

## Integrity, idempotency, and migration

Identifier design becomes especially important during data migration and system integration.

A migration from natural primary keys to surrogate primary keys generally requires a mapping between old business identifiers and new internal IDs. Dependent tables must be updated carefully, with foreign-key constraints and uniqueness checks applied before old identifiers are retired.

A reliable migration preserves the old natural identifier as a unique candidate key when the domain still requires it. Removing it without an alternative uniqueness rule can permit duplicate business entities even though every surrogate ID remains unique.

External ingestion should treat source identity as a separate concept. A source record can be imported repeatedly, but repeated ingestion should resolve to the same internal entity or be rejected if its meaning conflicts with the existing mapping.

A robust reconciliation workflow distinguishes:

- **Exact match:** the same authoritative source identity and compatible payload already exist.
- **Natural-key match:** the incoming record refers to an existing business identity under documented domain rules.
- **New entity:** no existing identity matches, so a new internal ID can be allocated.
- **Conflict:** the same natural or source key points to incompatible entities or data.

A matching natural key does not automatically justify merging two records. Legal restructurings, reused identifiers, source-data errors, and changes in jurisdiction may require human review or an explicit reconciliation policy.

## Performance and operational considerations

Key width affects storage and index behavior, especially when a primary key is copied into many foreign-key columns and secondary indexes.

A 64-bit integer uses eight bytes for the key value itself. A UUID uses sixteen bytes, while a natural string has variable storage requirements. Actual row and index sizes are larger because of database metadata, tuple overhead, alignment, and index structure.

Sequential integers and time-ordered UUIDs can improve insertion locality compared with uniformly random keys in some workloads. The outcome depends on write volume, cache behavior, index maintenance, clustering, and database implementation.

Identifier generation should match the deployment architecture. Centralized systems can use database sequences. Independently operating services may prefer UUIDs to avoid coordination. Distributed allocation must still account for retries, persistence, and duplicate requests.

Identifiers should not carry accidental business meaning. A surrogate ID is not a reliable count of registered customers, a transaction timestamp, or proof that one record was created before another. Likewise, an email address or tax identifier should not be exposed as an access credential.

## Common failure modes

**Treating a unique surrogate as proof of unique business entities.** Generated IDs prevent primary-key collisions, not duplicate customers. Domain uniqueness needs separate constraints and reconciliation logic.

**Using mutable attributes as permanent identity.** Names, email addresses, addresses, and some legal identifiers can change. If they are primary keys, every dependent relationship may require a coordinated update.

**Assuming a natural key is globally unique.** Many identifiers are unique only within a jurisdiction, organization, source system, or effective period. The scope belongs in the key definition.

**Normalizing without an authoritative rule.** Lowercasing or stripping characters may merge values that a source system considers distinct. Normalization must be explicit, consistent, and domain-correct.

**Generating IDs with process-local counters in distributed systems.** Multiple processes can allocate the same values. Use a coordinated allocator or sufficiently strong distributed identifier strategy, and retain database constraints.

**Relying on a pre-insert existence check.** Two concurrent transactions can both observe that a key is absent. The unique constraint must be the final authority, and the application must handle a conflict by resolving or rejecting the existing identity.

**Using hashes as if collisions were impossible.** Cryptographic digests are useful for deterministic representations, but original identifiers and explicit uniqueness rules should remain available for reconciliation.

**Assuming UUIDs eliminate authorization risks.** An unpredictable ID may reduce casual enumeration, but authorization must still verify whether a caller can access the referenced entity.

**Expecting gap-free integer sequences.** Database sequence allocation is designed for uniqueness and concurrency, not gap-free numbering. Business documents requiring controlled sequential numbers need a separate transactional numbering policy.

## Design decision criteria

A surrogate primary key is often a practical choice when entities have mutable business identifiers, many dependent tables, multiple source systems, or long lifecycles. Retaining unique natural identifiers alongside it preserves business integrity and supports external reconciliation.

A natural primary key may be appropriate when the domain provides a genuinely stable, compact, authoritative identifier and the costs of propagating it are acceptable.

A composite key is appropriate when uniqueness depends on multiple domain attributes and those attributes have clear, stable semantics. A UUID is useful when identifier generation must occur independently across services, while an integer sequence is often efficient for centralized relational workloads.

The key design should document what each identifier means, who owns its uniqueness, how corrections are handled, how external records are mapped, and which database constraints enforce the resulting invariants.
